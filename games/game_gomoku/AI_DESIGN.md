# 五子棋 AI 设计方案

本文定义五子棋 AI 的长期架构和可验收路线。目标不是实现一个“看起来会下棋”的
模式评分器，而是在桌面端资源约束下，逐步构建具有强制杀棋、稳定搜索、自我对弈训练
和客观强度评测能力的高水平引擎。

## 1. 规则基线

- 棋盘：15×15。
- 规则：自由五子棋（Freestyle Gomoku），横、竖或斜线连续五子及以上获胜。
- 黑方先行，不设三三、四四、长连禁手。
- 第一阶段玩家执黑、AI 执白；引擎接口本身必须支持任意一方执子。
- 棋局规则仍由 `logic.py` 负责；AI 不复制或改变胜负规则。

如果以后加入连珠（Renju）规则，应新增独立规则策略，不能把禁手判断混入自由规则搜索。

## 2. “顶级”的验收定义

强度必须由自动化基准证明，而不是由启发式评分大小推断。

| 维度 | 首个可玩版本 | 强力 CPU 版本 | 神经网络版本 |
| --- | ---: | ---: | ---: |
| 一步胜/一步防 | 100% | 100% | 100% |
| 标准 VCF 战术集 | ≥ 95% | 100% | 100% |
| 标准 VCT 战术集 | ≥ 75% | ≥ 95% | ≥ 98% |
| 普通难度响应 P95 | < 500 ms | < 500 ms | < 500 ms |
| 专家难度响应 P95 | < 2 s | < 2 s | < 2 s |
| 非法落子/超时崩溃 | 0 | 0 | 0 |

另维护固定时间控制下的 Elo 联赛。候选引擎只有在至少 1,000 盘交叉对局中达到预设
置信门槛，才替换当前稳定版。对称局面需要交换先后手，避免先手优势污染结论。

## 3. 总体架构

```text
Pygame 游戏循环
    └── AI Controller（后台计算、取消、超时、难度）
          └── Engine API（局面快照 → SearchResult）
                ├── 即时胜负与强制应手
                ├── VCF / VCT 威胁空间搜索
                ├── 迭代加深 PVS / Alpha-Beta
                │     ├── 候选点生成与排序
                │     ├── 增量棋型评估
                │     └── Zobrist 置换表
                └── 后期：Policy-Value 网络 + MCTS
```

必须坚持两层棋盘模型：

1. `logic.GameState` 是 UI 和规则层的可靠、不可变事实来源。
2. 搜索内部使用紧凑的可落子/撤销局面，维护增量哈希、邻域和棋型缓存，避免每个节点
   重建 15×15 元组。

AI 返回建议落子和分析信息，最终落子仍必须调用 `logic.place_stone`，从而保证 AI 永远
不能绕过规则。

## 4. 稳定接口

建议的公共接口：

```python
@dataclass(frozen=True)
class SearchLimits:
    time_ms: int
    max_depth: int | None = None
    max_nodes: int | None = None


@dataclass(frozen=True)
class SearchResult:
    move: Position | None
    score: int
    depth: int
    nodes: int
    elapsed_ms: int
    principal_variation: tuple[Position, ...]
    forced_win: bool = False


def choose_move(
    state: GameState,
    limits: SearchLimits,
    cancel: Callable[[], bool] | None = None,
) -> SearchResult: ...
```

约束：

- 相同局面、限制和随机种子必须可复现，方便回归测试。
- 达到时间限制时返回最后一次完整迭代的最佳着法，不能返回半搜索结果。
- 取消、重开、悔棋或退出后，旧搜索结果不得污染新棋局。
- 空棋盘默认走天元，不启动昂贵搜索。
- `move` 只有在无合法着法时才允许为 `None`。

## 5. 强力 CPU 引擎

### 5.1 搜索顺序

每个节点按以下优先级处理：

1. 己方立即成五。
2. 阻挡对方立即成五。
3. 己方 VCF（连续冲四取胜）搜索。
4. 对方 VCF 防守。
5. 己方 VCT（连续威胁取胜）搜索。
6. 进入迭代加深 PVS；叶节点使用威胁延伸，避免在活四前静态截断。

五子棋中普通的静态叶节点很容易产生“地平线效应”，因此战术搜索是主搜索的正确性
组件，不只是一个性能优化。

### 5.2 候选点生成

- 首先加入所有成五点、必防点、活四/冲四和活三相关点。
- 其余只考虑距已有棋子切比雪夫距离不超过 2 的空点。
- 不能用邻域裁剪丢弃任何已识别的强制攻防点。
- 使用上次迭代最佳着、置换表着法、杀手着法、历史启发表和棋型优先级排序。
- 对完全对称的空棋盘和开局局面进行对称规约，减少重复分支。

### 5.3 棋型与评估

棋型识别基于经过落点的四个方向，至少区分：成五、活四、冲四、双四、活三、眠三、
活二以及复合威胁。评估应从“双方下一步能形成什么”出发，而不是简单累计连子长度。

实现要求：

- 棋型表由程序生成并由穷举测试验证，避免散落的字符串特判。
- 落子和撤销只更新受影响的行、列和两条斜线。
- 胜负分数必须高于全部非终局分数之和，并编码距胜负手数，让引擎偏好更快取胜、
  更慢落败。

### 5.4 搜索基础设施

- 迭代加深 + PVS（Principal Variation Search）。
- Zobrist 哈希和固定容量置换表，记录深度、上下界类型、分数与最佳着。
- Aspiration window 仅在基线搜索稳定后启用。
- 每 1,024 个节点或更频繁检查时间与取消信号。
- 对杀棋节点保留完整正确性；任何激进裁剪都必须用战术集证明不会漏杀。
- 初期不采用空步裁剪。五子棋存在大量 zugzwang 式强制应手，未经证明的空步假设风险高。

## 6. 神经网络与自我对弈

纯 CPU 搜索负责先交付一个强、可解释、可离线运行的版本。神经网络是后续提高上限的
独立训练管线：

- 输入：当前方/对手棋子平面、最后若干步、轮次、规则等 15×15 特征平面。
- 网络：轻量残差 CNN，输出 225 维策略和一个局面价值。
- 搜索：PUCT MCTS；每次扩展前仍运行确定性的即时胜负和强制应手检测。
- 数据：自我对弈生成 `(局面, 搜索策略, 最终胜负)`，使用棋盘八种旋转/镜像增强。
- 晋级：新模型与稳定模型进行交换先后手的竞技场对局，通过统计门槛才发布。
- 部署：模型版本、规则版本和输入编码版本必须一起记录；桌面包在无加速设备时自动回退
  到 CPU 引擎。

最终形态采用混合引擎：神经网络负责候选先验和长程局面判断，VCF/VCT 搜索负责战术
正确性。单独依赖 MCTS 不足以保证短时限下不漏一步杀。

## 7. 线程与用户体验

AI 搜索绝不能阻塞 Pygame 主循环。控制器在后台工作，并为每次请求分配递增的局面代号：

- 玩家落子后显示“AI 思考中”，暂时禁止再次落子。
- 悔棋、重开、切换模式、返回菜单时立即取消搜索。
- 只接受与当前棋盘哈希和局面代号都匹配的结果。
- 专家难度也要持续刷新画面、响应窗口关闭与全局快捷键。
- 可选展示思考时间、搜索深度和主要变化，但不让调试信息成为游戏逻辑依赖。

## 8. 代码边界

建议新增：

```text
games/game_gomoku/ai/
├── api.py          # 稳定接口与返回值
├── controller.py   # 后台任务、取消和过期结果保护
├── position.py     # 可落子/撤销的搜索局面
├── patterns.py     # 棋型识别与增量特征
├── movegen.py      # 候选点与排序
├── threats.py      # VCF / VCT
├── search.py       # 迭代加深 PVS
├── evaluate.py     # 静态评估
└── zobrist.py      # 哈希与置换表
```

神经网络训练代码放在独立的 `training/gomoku/`，不能让 Pygame 运行时强制依赖训练框架。

## 9. 测试与基准

### 正确性

- 棋盘转换与 `GameState` 完全一致。
- 任意合法的 `make_move` / `unmake_move` 往返后，棋盘、行棋方和哈希完全恢复。
- 旋转/镜像后的局面，最佳着和分数保持对应关系。
- 置换表开关不能改变固定深度的最终分数。
- 超时与取消始终返回合法结果且不泄漏后台线程。

### 战术集

- 一步胜、一步防、双向成五。
- 活四、冲四、双四、四三、双三。
- 必须唯一防守、表面进攻但实际被反杀、边角棋型。
- VCF/VCT 正例与容易误判的反例。

每个失败局面保存为可读记录，成为永久回归用例。

### 性能与强度

- 记录每秒节点、有效分支因子、置换表命中率、各深度耗时和 P95 响应。
- 固定机器、固定种子、固定时间控制进行版本联赛。
- 同时保留旧版本、纯随机、贪心棋型和公开基准引擎作为锚点。

## 10. 分阶段交付

### M1：可靠且可玩

- 搜索局面、增量 Zobrist、候选生成、即时胜负/防守。
- 迭代加深 Alpha-Beta、基础棋型评估、后台控制器。
- 接通人机入口、取消、悔棋和重开。

### M2：战术强引擎

- 完整棋型表、PVS、置换表和稳定走法排序。
- VCF 搜索与战术回归集。
- 三档难度和性能基准。

### M3：专家级 CPU 引擎

- VCT、威胁延伸、对称规约、开局库。
- 自动版本联赛和 Elo/置信区间报告。
- 基于基准数据优化热点，必要时将搜索核心迁移到原生扩展。

详细接口、实施顺序和验收门槛见 [M3_DESIGN.md](M3_DESIGN.md)。

### M4：自我对弈神经网络

- 数据生成、训练、竞技场晋级、模型版本管理。
- Policy-Value 网络与 MCTS，保留确定性战术求解器。
- 对 CPU 引擎和外部强引擎进行长期评测。

## 11. 当前进度

- M1 已完成：可落子/撤销局面、Zobrist、候选生成、迭代加深搜索、后台控制器和人机入口。
- M2 已完成：精确复合棋型分类、PVS、容量受控置换表、VCF 求解器、三档难度和战术回归集。
- M3 详细设计已完成，实施待开始：VCT、威胁延伸、对称规约、开局库和自动 Elo 联赛。
