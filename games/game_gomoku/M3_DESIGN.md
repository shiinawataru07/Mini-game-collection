# 五子棋 AI M3：专家级 CPU 引擎设计

本文把总体路线中的 M3 拆成可直接实施和验收的工程方案。M3 的目标是在不引入训练框架、
不依赖网络并保持专家难度单步 P95 小于 2 秒的前提下，显著提高中盘强制进攻、叶节点
战术正确性和开局稳定性，同时建立可信的版本强度晋级机制。

## 1. 范围与非目标

M3 包含：

- VCT（Victory by Continuous Threats，连续威胁取胜）证明搜索。
- 威胁静态延伸，降低主搜索的地平线效应。
- 棋盘八种旋转/镜像的对称规约。
- 带版本和规则校验的自由五子棋开局库。
- 自动竞技场、Elo/置信区间报告和版本晋级门槛。
- 搜索阶段、置换表和战术求解器的细粒度诊断数据。
- 基于实测热点决定是否迁移原生核心。

M3 不包含：

- 连珠禁手规则或其他规则变体。
- 神经网络、MCTS、自我对弈训练和 GPU 部署；这些属于 M4。
- 联网排行榜、账号系统或外部服务。
- 未经战术证明验证的空步裁剪等激进搜索技巧。

## 2. M3 完成标准

| 维度 | M3 门槛 |
| --- | ---: |
| 一步胜/一步防 | 100% |
| M2 VCF 回归集 | 100%，不得回退 |
| VCT 正例集 | ≥ 95% |
| VCT 反例误报 | 0 |
| 八种对称的着法/分数一致性 | 100% |
| 开局库非法着法或规则不匹配 | 0 |
| 标准难度单步耗时 P95 | < 500 ms |
| 专家难度单步耗时 P95 | < 2,000 ms |
| 取消请求到停止计算 P95 | < 50 ms |
| 自动联赛非法着法/超时崩溃 | 0 |
| 相对 M2 的 Elo 提升下界 | 95% CI 下界 > +25 Elo |

Elo 晋级使用不少于 1,000 盘成对对局。战术正确性和稳定性是硬门槛，即使 Elo 提升也
不能抵消 VCF/VCT 误报、非法着法或响应时间回退。

## 3. 搜索流水线

```text
局面快照
  ├── 合法性、立即成五、唯一必防
  ├── 对称规约后的开局库查询
  ├── 己方 VCF / VCT 证明搜索
  ├── 对手强制威胁审计与防守候选提升
  └── 迭代加深 PVS
        ├── 对称置换表
        ├── 威胁优先走法排序
        └── 叶节点威胁延伸
```

所有阶段共享同一个硬截止时间和取消信号。专家难度的建议软预算为：

- 开局查询最多 5 ms；命中后立即返回。
- VCF 与 VCT 共用最多 45% 的软预算，未使用时间自动留给 PVS。
- PVS 至少保留 45% 的初始预算。
- 剩余 10% 是调度余量，不形成额外等待。

软预算只决定是否启动下一轮战术深度；硬截止时间始终由统一的 `TimeBudget` 控制。
不得让独立求解器各自拥有不相干的计时逻辑。

## 4. VCT 证明搜索

### 4.1 VCF 与 VCT 的边界

现有 VCF 只允许每个非终结进攻立即形成四，因此对手通常只有一个必防点。VCT 还允许
活三、双三、四三等威胁：它们可能有多个防守方式，搜索不再是一条强制直线，而是一棵
AND/OR 证明树。

- 进攻节点是 OR：只需找到一个能强制取胜的进攻着。
- 防守节点是 AND：所有有效防守着都必须仍然被证明失败。
- 任一防守分支无法证明，当前进攻着就不能标记为强制胜。

### 4.2 威胁模型

```python
@dataclass(frozen=True)
class Threat:
    gain: Position
    kind: ThreatKind
    winning_points: tuple[Position, ...]
    continuation_points: tuple[Position, ...]
    dependency_cells: frozenset[Position]


@dataclass(frozen=True)
class ProofNode:
    move: Position
    kind: ThreatKind
    defenses: tuple[tuple[Position, "ProofNode | None"], ...]
```

- `gain` 是本轮进攻落点。
- `winning_points` 是下一手直接成五的位置。
- `continuation_points` 是能把当前威胁升级为四或复合威胁的位置。
- `dependency_cells` 是该威胁成立必须保持空闲或特定占用状态的局部格点。
- `ProofNode` 保存所有有效防守分支，构成可复验的必胜证书。

第一版 VCT 进攻候选只接受 `FIVE`、`DOUBLE_FOUR`、`OPEN_FOUR`、`FOUR_THREE`、
`FOUR`、`DOUBLE_THREE` 和 `OPEN_THREE`。眠三和活二只参与静态评估，不进入证明树。

### 4.3 防守着生成

防守集合必须包括：

1. 防止立即成五的所有点。
2. 当前威胁的获胜点、延续点和依赖区域内能破坏威胁的点。
3. 防守方能够立即成五的反击。
4. 防守方能够形成四或更强威胁的抢先反击。
5. 同时阻挡威胁并制造反威胁的复合着法。

依赖区域之外、不能产生四且不改变威胁线路的着法等价于“虚着”，进攻方可以按原证明
继续。实现中仍需用证书验证器模拟代表性虚着，防止依赖区域计算遗漏远端斜线影响。

### 4.4 搜索、缓存与证明验证

- 使用迭代威胁深度：1、2、3……，只有完整一轮结束才能发布证明。
- 失败缓存键至少包含 `(canonical_hash, attacker, remaining_threats)`。
- 成功结果保存完整证明树；界面只展示其中一条主要变化。
- 证明树生成后必须由独立的 `verify_proof` 重放，不复用求解器的成功缓存。
- 验证器检查每一步合法性、威胁分类、全部防守分支和最终成五。
- 超时或取消得到的是“未知”，绝不能等同于“无强制胜”或保存为永久失败缓存。
- 证明分数继续编码距离：更短的已证明胜利优先。

建议将 VCF 保留为速度更快的专用求解器，VCT 在 VCF 未命中后运行，而不是用通用 VCT
替换已经验证稳定的 VCF。

### 4.5 对手威胁审计

只会证明己方必胜仍可能在安静评分中漏掉对手的潜在杀棋。己方 VCF/VCT 未命中后，使用
较浅的对手视角证明搜索进行威胁审计：

- 若对手存在证明树，将根进攻点、依赖点和能制造抢先四的己方着法提升为防守候选。
- 每个候选防守落下后重新验证对手证明是否被破坏，不能假设占住第一进攻点就是唯一防法。
- 防守审计只改变候选完整性和排序，不直接返回“必败”；最终分数仍由正常 PVS 验证。
- 专家难度审计深度与 VCT 相同，标准难度使用较浅上限，入门难度只审计 VCF。

战术集必须包含唯一预防点、多个可防点、无法防守和看似防住但仍有转线杀棋四类局面。

## 5. 威胁静态延伸

普通 PVS 到达深度零时，如果局面仍存在四或活三，直接静态评分会漏掉即将发生的强制
交换。M3 新增类似静态搜索的 `threat_quiescence`：

```python
def threat_quiescence(
    position: SearchPosition,
    alpha: int,
    beta: int,
    remaining: int,
) -> int: ...
```

延伸顺序：

1. 当前方立即成五。
2. 对手立即成五时的全部必防点。
3. 当前方成四、双四、四三。
4. 对手成四后的强制防守。
5. 剩余额度允许时，扩展双三和活三。

约束：

- 默认最大延伸为 6 个半回合，专家难度最多 10 个半回合。
- 每次真实落子都减少额度，因此不会形成空循环。
- 有对手必杀时不能使用普通 `stand pat` 分数直接截断。
- 静态延伸使用独立的置换表深度域，不能把延伸结果冒充普通固定深度结果。
- VCF/VCT 已证明的分数可以直接复用；未完成的证明不得影响 Alpha/Beta 界。

## 6. 八种对称规约

15×15 正方形棋盘有 8 种等价变换：恒等、旋转 90/180/270 度，以及镜像后的四种旋转。

新增 `symmetry.py`：

```python
class Transform(IntEnum): ...


def transform_move(move: Position, transform: Transform) -> Position: ...
def inverse_move(move: Position, transform: Transform) -> Position: ...
def canonical_key(position: SearchPosition) -> CanonicalPosition: ...
```

`SearchPosition` 在落子和撤销时增量维护 8 个 Zobrist 哈希。取数值最小的哈希作为规范
方向，并记录实际方向到规范方向的变换。置换表和开局库均使用规范键：

- 写入最佳着前，把实际着法转换到规范方向。
- 读取后使用逆变换还原，并再次检查着法合法性。
- 哈希相同的极低概率冲突由第二个独立 64 位 lock key 校验。
- 行棋方必须包含在 8 个哈希中。

对称规约不能改变搜索分数和候选完整性。所有棋型、VCF/VCT 和开局用例都要自动生成
8 个变换版本进行回归。

## 7. 开局库

### 7.1 运行时格式

开局库是只读、惰性加载的数据文件，建议放在：

```text
games/game_gomoku/ai/data/openings.freestyle15.json
```

顶层元数据至少包含：

```json
{
  "format_version": 1,
  "ruleset": "freestyle",
  "board_size": 15,
  "max_ply": 10,
  "engine_version": "m3",
  "positions": {}
}
```

每个局面使用双 64 位规范键，条目记录规范方向着法、样本数、胜率、来源和最低置信度。
加载时必须验证格式、规则、棋盘大小、校验和及全部着法合法性；任何异常都只禁用开局库，
不能阻止游戏启动。

### 7.2 选着策略

- 专家难度选择置信下界最高的着法，保持确定性。
- 标准难度可在分数接近的多个着法间按固定局面种子加权选择，仍可复现。
- 入门难度只使用天元和极浅条目，避免开局很强、中盘突然变弱的割裂感。
- 第 10 手后、条目置信度不足或局面不匹配时立即回退搜索。
- 开局着最终仍由 `logic.place_stone` 验证。

开局数据构建脚本与运行时分离。第一批条目应来自人工校验的小型自由规则开局集和 M3
长时限交叉分析；未经验证的普通自我对弈胜率不能直接进入发布库。

## 8. 自动竞技场与 Elo

### 8.1 对局协议

新增纯逻辑竞技场，不依赖 Pygame：

```python
@dataclass(frozen=True)
class EngineSpec:
    name: str
    choose: EngineCallable
    limits: SearchLimits
    feature_set: str


@dataclass(frozen=True)
class GameRecord:
    opening_id: str
    black: str
    white: str
    moves: tuple[Position, ...]
    result: Literal["black", "white", "draw"]
    termination: Literal["five", "draw", "illegal", "timeout", "error"]
```

- 每步只传不可变 `GameState`，最终落子调用规则层。
- 非法着、异常或超过硬时限均记该引擎负，并保留完整诊断。
- 对局记录使用可读 JSONL，可由测试复放。
- 联赛默认使用节点上限保证可复现；另运行真实时间控制检查桌面体验。

### 8.2 开局套件与配对

准备 250 个经过验证、双方均未形成强制胜的浅开局。每个开局进行四盘：

1. 原方向，候选执黑。
2. 原方向，候选执白。
3. 镜像方向，候选执黑。
4. 镜像方向，候选执白。

总计 1,000 盘。统计重采样以“同一基础开局的四盘”为一个样本组，不能把高度相关的
镜像和换色对局当成四个独立样本。

### 8.3 评分与晋级

- 胜计 1、和计 0.5、负计 0。
- Elo 点差使用逻辑斯蒂模型估计。
- 95% 置信区间对开局组进行至少 10,000 次 bootstrap。
- 报告总 Elo，同时单列执黑、执白、开局阶段和中盘阶段结果。

候选版本晋级必须同时满足：

1. 至少 1,000 盘，无非法着、异常和失控超时。
2. 相对稳定版的 Elo 95% CI 下界大于 +25。
3. 执黑和执白任一分项的 CI 下界不得低于 -10 Elo。
4. VCF 维持 100%，VCT 正例达到 95%，VCT 反例误报为 0。
5. 专家 P95 小于 2 秒，标准难度 P95 小于 500 ms。
6. 取消响应 P95 小于 50 ms，内存峰值不比稳定版增长超过 25%。

发布报告必须记录 Git 提交、Python 版本、机器信息、引擎配置、随机种子、开局集版本和
开局库校验和，避免无法复现的“幽灵 Elo”。

## 9. 搜索诊断

新增内部 `SearchDiagnostics`，至少记录：

- 主搜索、静态延伸、VCF、VCT 节点数。
- 各阶段耗时和最终完成深度。
- 置换表 probes、hits、cutoffs、collisions。
- 对称规范命中数和开局库命中来源。
- 候选数量、有效分支因子、PVS 窄窗重搜次数。
- VCT 证明深度、分支数和验证耗时。
- 停止原因：完成、硬超时、节点上限或用户取消。

这些数据不进入游戏规则。`SearchResult` 只增加带默认值的 `source` 和可选诊断对象，保持
现有调用兼容：

```python
source: Literal["book", "vcf", "vct", "search"] = "search"
diagnostics: SearchDiagnostics | None = None
```

## 11. 实施顺序

### M3.1：可观测性与对称基础

- 统一 `TimeBudget` 和诊断数据。
- 实现 8 种变换、逆变换和 8 路增量哈希。
- 置换表切换到规范键，完成全套对称性质测试。

这是后续开局库和 VCT 缓存的共同基础，必须先完成。

### M3.2：威胁静态延伸

- 独立实现 `threat_quiescence`。
- 建立地平线效应正例、静态安静局面和反杀回归集。
- 对比关闭/开启延伸的固定深度节点数和正确率。

### M3.3：VCT 与证明证书

- 从四、四三、双三、活三逐级开放候选类型。
- 先实现 AND/OR 搜索，再实现不共享成功缓存的证书验证器。
- 建立至少 200 个正反局面；误报必须为 0。

### M3.4：开局库

- 实现格式、规则、校验和及合法性验证。
- 构建第一版不超过第 10 手的小型高置信开局库。
- 将开局查询接入对称规范和搜索来源诊断。

### M3.5：竞技场和版本晋级

- 实现纯逻辑对局、成对开局、JSONL 复放。
- 实现分组 bootstrap、Elo 报告和硬性晋级门槛。
- 保存 M2 稳定版作为首个基线工件，完成首轮 1,000 盘报告。

### M3.6：分析与优化

- 用诊断数据定位耗时，优先优化候选生成、棋型分析和威胁求解。
- 只有 Python 热点持续占总耗时 60% 以上，且专家 P95 或 VCT 正确率无法达标时，才将
  `position/patterns/vct` 迁移到可选原生扩展。
- 原生扩展必须保留 Python 回退，并通过完全相同的战术和对称测试。

## 12. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| VCT 漏掉防守而误报必胜 | AND 节点全防守、反威胁纳入、独立证书验证、反例硬门槛 |
| 静态延伸导致搜索爆炸 | 只扩展强威胁、独立额度、统一硬截止、诊断分支因子 |
| 对称着法映射错误 | 8 变换往返性质测试、读表后合法性复验 |
| 开局库污染规则或损坏 | 元数据、双哈希、校验和、逐着合法性验证、失败自动回退 |
| Elo 被先手优势或重复局面虚高 | 换色、镜像、按开局组 bootstrap、分颜色报告 |
| 时间波动导致不可复现 | 强度联赛用节点限制，墙钟测试只用于体验和超时验收 |
| 过早原生化增加构建复杂度 | 先测量热点，达到明确迁移阈值后再决定 |

## 13. M3 结束时的交付物

- 一个能给出并验证 VCT 必胜证书的专家 CPU 引擎。
- 不漏明显强制交换的威胁静态延伸搜索。
- 对置换表、VCT 和开局库统一生效的对称规约。
- 可校验、可禁用、损坏可安全回退的开局库。
- 可复放的 1,000 盘版本联赛与带置信区间的 Elo 报告。
- 记录正确率、响应时间、内存和搜索热点的 M3 验收报告。

只有以上交付物全部通过硬门槛，设计文档中的 M3 才能标记为完成。
